# 把 VM 加进白盒 AES：可行范围与技术前提

## 一、先看数字：现有 VM 够不到这张表

`include/hsvm/machine.h:47-48`：VM 内存 **4096 字节**，寄存器 **16 个 32 位**，
ISA 16 条 opcode（`Ld/St` 只能寻址 4 KiB 内的 4 字节对齐字）。

白盒 AES 一轮需要：16 次查表，每次进一张 **64 KiB** 表（10 轮 + 逆向路径共 66 MiB）。
一轮 16 次 × 每次至少 16 个 4 KiB 页 = 256 次页切换，9 轮 ≈ 2300 次；
而 VM 每步还要解释/执行开销。**用现有 ISA 表达这条路，代价比收益大两个数量级。**

所以"把 VM 加上"在这个仓库里只有三种可能的落点，必须选一个：

| 方案 | 覆盖什么 | 代价 | 评价 |
|---|---|---|---|
| A. VM 化外围（P0 索引散布、DFA 比对、状态打包） | 只覆盖非查表部分 | 小 | 攻击者读的是表，收益≈0，纯装饰 |
| B. 给 ISA 加"外部表读取"opcode | 覆盖轮函数骨架 + 查表 | 中（改 ISA 与四层实现） | 唯一能让 VM 真正进热路径的路 |
| C. 把轮函数写成字节码 + 表分页进 VM 内存 | 全路径 | 大（ISA 内存模型要重做） | 性能不可接受（GB 级访存） |

## 二、推荐方案 B 的具体形状

在 ISA 单一真源（`HSVMOpcodes.def`）追加两条：

```
HSV_OP(Tld, 0x10)   // dst = Table[reg[a] + imm32]  (32 位读, 越界/未对齐 → fault)
HSV_OP(Tst, 0x11)   // Table[reg[a] + imm32] = reg[b]
```

语义约定（必须与现有 `Ld/St` 一致）：小端、4 字节对齐、越界即 fault 且 pc 不前进；
`Table` 是宿主进程提供的一段只读区，基址由 `hsvm_entry` 的第二个参数传入（或宿主导出的全局符号）。

落地要改的四处（一处漏掉就会"编译通过但语义分叉"，这是此前的教训）：
1. `HSVMOpcodes.def`：加两条（唯一真源）→ `sync_isa.py --write` 重新生成 `isa.h`；
2. `machine.cpp`：执行语义 + fault 判定；
3. `semantics.h`：oracle 同一套语义（`test_semantics` 补断言）；
4. `lower.cpp` + `HSVMLowering.cpp`：lowering 与 pass 的发射路径；
5. `tests/`：`diff`、`lower_full`、`fuzz_threeway`、`vmp_gate` 全部要覆盖新 opcode。

预计：ISA 与三层实现 ~半天，测试与 gate 扩展 ~半天，demo 集成（把轮骨架写成 HSV 程序）~一天。

## 三、必须先接受的前提

即使做完 B，**攻击者仍然静态读表**：`Tld` 只是换了取值方式，表还是明文（或被我们掩码的表）。
VM 在这条路径上买到的是"轮控制流被字节码化"，买不到"表不可读"。
所以 B 的正当理由是"链路完整性 + 演示 VM 真能承载密码学内核"，
而不是"让 wbaes 更难逆向"——后者的瓶颈在数据层，不在指令层。

## 四、现在没有动代码的原因

ISA 是协议的一部分（`protocol_sha256` 绑定它），加 opcode 会让既有 gate 与随机测试的基线失效。
这需要一次明确的版本升级（ISA v2），而不是在导出产物上顺手加一个 pass。
在得到确认前不改 `HSVMOpcodes.def`，避免留下"gate 绿但语义未覆盖"的假状态。
