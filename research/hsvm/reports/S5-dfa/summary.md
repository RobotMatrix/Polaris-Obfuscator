# 阶段 5 前置：对 wbaes 二进制的 DFA 实测（外部报告 + 本地复核）

样本：`demos/wbaes/exported-binaries/final-max-10pass/hybrid-baked/macos/wbaes_baked_keyrot_ec326393`
（SHA-256 `6336604ece6eda73…`，正是本次换钥后构建的那个二进制）

外部报告：`wbaes_recovery.zip`（WRITEUP.md / recover_key.py / recovered_key.json）

## 一、外部结论

- 恢复出的 AES-128 密钥：`ec326393a354ed3ee5d1735964fd8a32`
- 第 10 轮子密钥：`42a4d3319fcbad4cb87761ccf388c07d`
- 方法：静态定位轮函数与状态缓冲区 → Unicorn 模拟加密核心 → **在第 9 轮前注入单字节故障**
  → 用 MixColumns 差分关系解第 10 轮子密钥 → 逆推密钥扩展
- 代价：**1 条正常密文 + 8 条故障密文**，9 条密文；无需枚举 128 位密钥，
  也无需还原 66 MiB 的查找表

## 二、本地独立复核（不是复述）

| 检查 | 方法 | 结果 |
|---|---|---|
| K10 是否正确 | 独立实现 AES-128 密钥扩展，从 K 推 K10 | `42a4d331…c07d`，与报告**一致** |
| 16 组验证向量 | 每组用 `openssl enc -aes-128-ecb` 重算 | **16/16 一致**（白盒密文 = 标准 AES 密文） |
| 故障样本数 | 读 `recovered_key.json` | 8 条，与报告一致 |

也就是说：报告里的密钥**确实**是这把钥，且该二进制在功能上就是标准 AES-128——
它的安全性完全依赖白盒表，而 DFA 绕过了表。

## 三、为什么 66 MiB 的表在这里毫无作用

DFA 不读表。它在**第 9 轮开始前**改一个状态字节，然后只看最终密文与正确密文的差异。
最后一轮没有 MixColumns，一个字节的输入差异只影响该字节对应的 4 个输出字节，
由此反解 `K10` 的 4 个字节；换故障位置即可拼出整个 `K10`。
表做得再大、编码再复杂，只要状态在内存里可写、密文可观测，这条路就成立。

这与 wbaes README §6 的自述一致（"仿射外部编码不抗 DFA"），现在是**实测确认**，
不是推断。

## 四、对我们文档的影响

1. **G2（DFA 攻击面）判定：失败。** 9 条密文取密钥，远低于任何预算门限。
2. 攻击者等级是 **A3**（可控运行时状态），比 A1/A2 都强；文档 §8 明确 A3 不在
   C1/C2 的防护范围内——所以这不是"C2 没做好"，而是选错了防护对象。
3. 对 HSV 构造的意义：C1/C2 都在"不改变状态可写性"的前提下做文章。只要状态缓冲区
   可写一次、密文可读一次，同样的 DFA 对任何表驱动实现都成立。
   真正对得上 DFA 的只有 C6 的**执行完整性检查**——但前提是它能发现"状态被改过"，
   而当前 C6 只有 ControlFlow/Memory 两个平面的被动比对，没有冗余计算或故障不变式。

## 五、应对的第一条：模型层冗余比对（本轮已实现）

| 手段 | 作用 | 代价 |
|---|---|---|
| 冗余计算 + 校验（同一轮算两遍比对） | 单字节故障会被抓 | 2× 计算 |
| 故障不变式（如轮输入/输出关系自检） | 抓特定位置的注入 | 每轮少量运算 |
| C6 把"状态自洽"加入 Memory 平面 | 与已有 shadow 机制复用 | 低 |

三者都属 C6 范畴，且都不需要白盒表更复杂；**加表不加安全**是这次实测最直接的教训。

**已实现第一条**：`Machine::setFaultCheckEnabled(true)` 让每步转移算两遍再比对——
这正是 DFA 的模型（一份被故障污染、一份正确）。检测到不一致时计入 `faultsDetected()`，
并向 Memory 平面报 mismatch。`injectFault(bit)` 是测试钩子，模拟攻击者注入单比特故障。

```
== c6: 34 pass, 0 fail ==     （新增 6 条：干净运行 0 检测 / 注入 1 次被检出 / 触发 Red）
```

**代价与边界（必须一起读）**：
- 转移计算 **2×**，与文档 §5.5 的 ≤3× 预算叠加后更不可能达标（该预算本就已失败）。
- 只能抓"发生在两份计算之间的"故障；攻击者在两份计算之前改状态、或直接改表/改检查器（A3），
  这一层抓不到。
- **wbaes 二进制本身没有这个检查**，所以那份 DFA 报告对它的结论不变：9 条密文取钥仍然成立。
