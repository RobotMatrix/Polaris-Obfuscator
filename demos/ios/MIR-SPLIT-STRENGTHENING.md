# MIR 函数拆分（Split Function）的强度分析与此处的强化路线

## 一、现在弱在哪（有出处）

`exported-binaries/README.md` 自己写了结论：
> Mach-O 的函数边界由符号表决定，块乱序/拆分全部发生在符号区间内部，
> 因此 **IDA 函数数量与混淆前一致**；若需要 IDA 函数数量虚增，
> 需要在 ASM 层为拆出块伪造函数符号——独立工作量，当前版本未实现。

所以当前拆分的实际效果只有三条：
```
① 函数体在符号区间内被打散到多个不连续位置（otool 能看到大量跨区 b 0x…）
② 块间夹脏字节与垃圾指令流，线性反汇编被打断
③ x86 版用 call/ret 改写返回地址（JAMPOUT），反编译器无法建模返回路径
```
  对"函数判断"这一目标，它的收益接近 0：**符号表一旦给出区间，工具就不需要猜边界**。

## 二、强化路线（按"对函数判断的实际破坏力"排序）

### S1 边界伪造：ASM 层为每个拆出块写函数符号 + FDE
- 做法：拆分后给每块生成 `.local` 符号（或 `.alt_entry`），并登记独立的
  `__eh_frame` FDE（unwind info）；块之间用 `ret`/`b` 连接而不是 fallthrough。
- 效果：IDA/Ghidra 的函数列表按符号/异常表枚举 ⇒ **函数数量虚增**，
  且每个假函数都"看起来完整"（有 prologue/epilogue）。
- 代价：ASM 层新 pass；FDE 增多会略增体积；必须保证调试器/崩溃回溯不炸。
- 这是唯一直接打在"函数判断"上的手段，其他都是间接。

### S2 打断"递归下降"：用计算分支而不是直接分支
- arm64 指令定长 4 字节，**没有 x86 那种"跳到指令中间"的重叠技巧**，
  所以 arm64 上唯一可靠的手段是 `br xN`（寄存器计算目标）+ 表驱动分发。
- 效果：递归下降无法静态得知后继块，块边界只能靠运行时或启发式；
  与 S1 叠加时，工具连"这是不是函数边界"都拿不到确定证据。
- 代价：每个跨块边沿一次间接跳转（分支预测友好度下降），需实测性能影响。

### S3 去符号 + 单一大区间：让工具必须自己找边界
- 做法：`-Wl,-x,-S` 去掉本地符号（导出表必须另清，见 `EXPORT-HARDENING`），
  把整个混淆区合成一个符号区间，内部只有计算分支。
- 效果：函数起点只能靠"prologue 模式 + 调用图 + 栈帧"推断，模型不确定；
  与 S1 的假边界一起，真边界会被埋在大量候选中。
- 代价：崩溃回溯与性能分析变难（这也是真实成本，不是纯收益）。

### S4 拆分粒度随机化 + 与合并联动
- 现有 `MergeFunction` 可以把多个函数合成一个；**先合再拆**会破坏 1:1 映射：
  工具看到的"函数"与原函数不再对应，即便恢复出边界，语义归属也是错的。
- 每构建随机粒度（比如 3–12 块/函数）可让签名跨构建不通用。

### S5 假函数（decoy）与假 prologue
- 插入永不执行的"函数"：完整 prologue/epilogue、合理的调用关系、
  指向真实表地址的引用，但结果不被使用。
- 效果：提高"函数数量"的噪声，且诱使分析者把时间花在错的地方。
- 代价：体积；必须保证不被优化掉（用 volatile/外部引用锚定）。

### S6 调用图隐匿（与拆分配合）
- 拆出的块之间用间接调用（`blr` 经混淆表）而不是直接 `bl`，
  使交叉引用（XREF）不产生"调用者列表"。
- 单独看这是弱手段（`IndirectCall` 已有），但与 S1/S3 叠加后，
  "谁调用谁"和"哪段属于哪个函数"两个信息同时缺失。

## 三、判据（必须可测，不写"更强"）

```
G1 函数数量：IDA/Ghidra 自动识别的函数数 ÷ 真实函数数（目标 ≥2.0）
G2 边界正确率：真实函数起始被正确识别的比例（目标 ≤50%）
   —— 用两份 ground truth 对照：编译期记录的真实符号地址 vs 工具输出
G3 入口发现成本：脚本从二进制定位 hy_mc_round / 取表循环所需的时间（对比基线）
G4 功能与性能：密文不变；每块耗时退化 ≤5%（arm64 上 S2 的间接跳转是主要成本）
G5 抗"符号恢复"：导出表/符号表/FDE 中不得出现原名（用 residual/macho_symbols.py 验）
G6 我方攻击不被增强：w16_extract / hs / consistency 的耗时不得下降（下降说明泄漏了新信息）
```

## 四、建议的实施顺序

1. **S1 + S3**：先把"函数边界"从工具手里拿走（假符号 + 去真符号），这是唯一直接命中目标的组合；
2. **S2**：在 arm64 上用计算分支打断递归下降，与 S1 配合把"边界"变成"猜测"；
3. **S4**：合并在前、拆分在后，破坏 1:1 语义映射；随机粒度每构建不同；
4. **S5/S6**：最后做，成本低但收益是噪声级，适合在 S1–S4 之后叠加。

## 五、诚实的边界

- 这些都是**提高逆向成本**，不改变"表可读 ⇒ 密钥可提取"（`demos/wbaes/FINAL-ASSESSMENT.md`）。
- arm64 无重叠指令技巧，所以强度上限低于 x86：x86 的 JAMPOUT 类效果在 arm64 只能靠计算分支近似。
- G1/G2 需要 IDA 或 Ghidra 的批量结果；没有这些工具时只能先测 S3+S5 的统计指标
  （函数起始候选数、prologue 模式数量），不能声称"函数判断被破坏"。
