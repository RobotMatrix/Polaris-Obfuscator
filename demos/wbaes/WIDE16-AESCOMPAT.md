# 用"白盒设计密码"的方法做 AES 兼容：16 位部分和构造

## 一、先分清"借方法"与"换算法"

SPNbox / WhiteBlock / SPACE 家族真正可借的是**方法**，不是它们的密码：
```
① 大表化（big tables）：把多字节运算预先算进 2^16 索引的表里
② 宽 S 盒：S 盒定义在 16 位字母表上，使"每字节 256 猜测"失效
③ Ni 类构造：用一个轻量置换生成大 S 盒，避免存 2^16 项
④ 配合掩码 + 打乱 + 假槽位（CHES 2021 已证 dummy slots 是关键项）
```
  但 AES 兼容意味着**黑盒函数被锁死**（同钥同明文必须输出同样密文），所以不能用 16 位 S 盒替换 AES 的 S 盒。
  能改的只有**内部分解**。

## 二、AES 兼容下把"合并宽度"从 8 位提到 16 位

关键观察：AES 的 MixColumns 是 **GF(2) 线性的**，所以按列把 4 个 lane 两两分组后，
存在 16 位→16 位的线性映射 L，使
```
列输出 = L( S(a⊕k0), S(b⊕k1) )  ⊕  L( S(c⊕k2), S(d⊕k3) )
```
把每个 L 预先算进一张 **2^16 项 × 16 位输出** 的表（128 KiB/张），
于是每列的合并变成 **两个 16 位字的 XOR**，而不是四路 8 位 XOR。

这正好打在前四代失败的根因上：
```
dl4/dl5/Z 路/融合代失败的共同原因 = 合并发生在 8 位宽
  ⇒ 必然存在一张 256×256 的 8 位值表可被分解 ⇒ 每密钥字节 2^8 次检验
16 位部分和 ⇒ 合并层的值是 16 位，256 项检验不再够，最少要 2^16
```
  代价：表体积约 128 KiB × 2 半 × 4 列 × 9 轮 × 2 方向 ≈ 36 MB（与融合代同量级，比现状 70 MB 小）；
  每列 2 次查表 + 1 次 XOR（比现在更少）。

## 三、必须承认的风险（不要预设它能赢）

1. **隐藏平移会跟着升级**：XOR 群作用从 (Z2)^8 变成 (Z2)^16，
   `hs_attack` 的"行共轭构成正则群 + 规范不变检验"很可能原样推广；
   若如此，收益只是常数项（2^8 → 2^16 次检验），不是渐近安全。
2. **L 是公开的线性映射**：攻击者已知 MC，可以把 L 还原成字节级关系，
   只要他能在某个环节拿到 8 位投影，就回到 2^8。
3. **AES 指纹仍在**（见 `FINGERPRINT.md`）：这一步只动合并宽度，不动"这是 AES"。

## 四、判据（这是实验，不是结论）

```
W1 兼容性：同钥同明文的密文必须与现状一致（7672415a…），四族/混合调度
W2 工作量因子：把 Decomp 推广到 16 位表后，每密钥字节的检验次数是否真的从 2^8 升到 2^16
   判据：要么给出"每字节 ≥2^16 且无捷径"的实测，要么明确写"只升到 2^k, k<16"
W3 若 hs_attack 的群作用可推广，则记录推广后的恢复成本，并给出是否仍是脚本级
W4 体积与每块耗时；W5 VM/DFA/封印/负向测试不变
```
  验收规则沿用上次修正：**闸门写"工作因子"，不写"某脚本失败"**。
