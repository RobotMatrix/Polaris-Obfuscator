# 白盒 AES 源码的 DFA 攻击面分析（2026-11-17）

对照外部报告（`wbaes_recovery.zip`：1 条正确 + 8 条故障密文，第 9 轮前注入单字节故障取回密钥）
逐条核对源码，说明**为什么那次攻击成立**，以及本轮补了什么、还剩什么。

## 一、攻击为什么成立：烘焙路径原本只有一次遍历

`demos/wbaes/demo_wbaes.cpp:1116-1121`

```cpp
#ifdef WBAES_BAKED
    (void)t1; (void)t2;
    hy_protect(in, out, 0);
    return 0;              // 永远返回成功
```

`hy_protect` → `hy_encrypt`（`wbaes_hybrid.inc`）原本是：

```cpp
for (r = 0; r < HY_MC_ROUNDS; r++) hy_mc_round(...);   // 9 轮，单份状态
hy_pair_map(..., s, out, ...);                          // 末轮映射, 无 MixColumns
```

三个致命点，正好对上外部报告的做法：

1. **单份状态，没有冗余**：任何一轮写进 `s[16]` 的故障都会一路传播到密文。
2. **没有输出校验**：`hy_protect` 无返回值、`enc_core` 恒返回 0，
   `encrypt()` 里的 `memcmp(back, in, 16)` 回环自检只在 `#else`（非烘焙）分支
   （`demo_wbaes.cpp:1085-1090`）。
3. **末轮无 MixColumns 是公开事实**：第 9 轮前改一个字节，只影响密文 4 个字节，
   于是 4 字节子密钥可用 4×256 试解，8 条故障覆盖 16 字节 —— 这就是报告里"9 条密文"的来源。

结论：那次 DFA 成功不是"表不够大"，而是**烘焙路径完全没有故障检测**。66 MB 表不参与这条路径。

## 二、非烘焙路径的防护，以及它自己的盲点

`demo_wbaes.cpp:1122` 起，非烘焙路径每轮用两套表 `t1`/`t2` 各算一次并比对：

```cpp
// DFA 深防: 轮级双算 — 每轮两套表各算一次, 比对一致才进下轮.
```

这比烘焙路径强，但仍有**共模**盲点：
- 两套表都由同一密钥派生、吃同一个输入 `in`；故障若发生在 `in` 或共享缓冲上，
  两份同时错，比对通过。
- 表本体在 `__DATA` 里（`__DATA,__hytab`），改表是**数据故障**，两份都读到被改的表。

## 三、本轮补的：烘焙路径改成两次独立遍历 + 比对

`wbaes_hybrid.inc`，`hy_encrypt` 现在：

```cpp
hy_encrypt_once(in, ct1, env, /*arm_fault=*/1);   // 第一次遍历
hy_encrypt_once(in, ct2, env, 0);                 // 第二次遍历, 独立缓冲
if (memcmp(ct1, ct2, 16) != 0) {
    wbaes_key::g_key_tampered |= 0x8000u;
    for (i) out[i] = wb_runtime_rand() & 0xFF;     // 垃圾, 不是故障密文
    return;
}
```

关键点：**检测到故障时不输出任何一份密文**。DFA 的前提是能拿到"正确密文与故障密文的差"，
输出随机数就切断了这个前提。代价是 2× 表访存。

攻击者拿不到可用的差分样本。

## 四、还没解决的（按可利用性排序）

1. ~~解密路径没有双算~~ **已修（本轮）**：`hy_decrypt` 拆出 `hy_decrypt_once`，同样两次遍历比对，
   不一致即毒化输出。正常构建下 `roundtrip: PASS`，说明双算没有破坏解密。
2. **共模故障**：同时把两次遍历的同一字节改掉（同址双故障）→ 比对通过。
   单故障防御不等于多故障防御。
3. **比对本身可被跳过**：A3 攻击者可 patch `memcmp` 或 `g_key_tampered` 的检查。
   客户端手段，无法根治；只能抬价。
4. ~~表本体可改~~ **已加检测（本轮）**：`gen_hybrid` 生成表时同时写出 `hy_seal.h`
   （全表 FNV-1a 与 stride=4096 抽样值），运行时首次调用做一次全表校验、之后每次调用做抽样校验。
   实测：把二进制里表区偏移 33768 的一个字节翻转后运行，输出变成随机垃圾、`vector-match: FAIL`。
   **仍然可绕**：校验代码本身可被 patch（A3），抽样只能发现 stride 4096 上的改动，
   两次抽样之间写入的改动不入检测。
5. **未覆盖**：故障注入到 `env`/`g_poison`（影响下标散布）时，两份会算出同样的错值。

## 五、与 KEY-ROTATION.md §7（表级密钥提取）的关系

那是**另一条**攻击面：静态读表，不注入故障。它的短板是第 0 轮没有输入侧编码，
表项直接等于 `S(x^k0) ^ S(y^k1)`。**本轮没有修这条**，原因如下：

把输入置换烘焙成一张 16×256 的表放进二进制，并不能阻止攻击者——他照样能读到这张表，
照样反推第 0 轮的 `x`。要真正抬高代价，需要让第 0 轮的表项不再等于那个式子，
例如把前置换与一层输出编码组合成两层结构，使静态求解退化成解一个组合方程。
这是重新设计第 0 轮编码，不是加个参数就行，工作量与"再做一次换钥 + 全表重生成"相当。

在没有做到之前，`extract_key.py` 仍然能在数秒内从二进制里取出密钥——
这件事必须写进任何对外说明里，不能因为做了 DFA 双算就当作已解决。
