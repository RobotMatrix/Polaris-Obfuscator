# 用仿射隐藏"多轮"结构：设计与实施计划

## 一、当前结构暴露了什么

`wbaes_hybrid.inc:68` 的运行时形状就是明文的轮数：

```c
for (int r = 0; r < HY_MC_ROUNDS; r++)
    hy_mc_round(HYKTAB, hy_enc_col(r, 0), r, 0, 1, s, n, env);
```

逆向者不需要理解表，只要数循环次数、看 `hy_enc_col(r, …)` 的步长，就知道是 9 轮 + 末轮。
表区布局也按 `(dir, round, col, side)` 分块（`hy_tag`），轮边界是**物理可见**的。

## 二、仿射能做与不能做的事（先把边界说清）

**能做的：轮间字节级仿射重编码（relabeling）。**
对每个轮边界 r 取一个仿射双射 `A_r(x) = a_r·x ⊕ b_r`（GF(2^8)，`a_r ≠ 0`），要求：

- 第 r 轮的输出侧表存 `A_r(v)`；
- 第 r+1 轮的输入侧表以 `A_r(v)` 为索引，即用 `S(A_r^{-1}(b) ⊕ k_{r+1})` 建表。

运行时**不需要任何新指令**：只是把第 r+1 轮表的行按 `A_r` 置换、把第 r 轮表的值按 `A_r` 编码。
收益：每轮看到的字节值都落在不同的仿射坐标系里，`表项 = S(pt ⊕ k)` 这条直线关系在轮内不再成立。

**不能做的：把轮数从代码里抹掉。**
`A_r` 是逐字节的，而轮间还有 `MixColumns`（4 字节线性混合）。若把 `A_r` 插在 MixColumns **之后**、
下一轮 SubBytes **之前**，则必须改写下一轮的 S 盒为 `S∘A_r^{-1}` —— 这只是"换了一张 S 盒"，
轮边界依然存在，循环依然是 9 次。要真正抹掉轮边界，需要 Chow 式的宽表融合
（把 MixColumns 折进 32 位宽表，轮与轮之间只剩 XOR），那是另一种数据规模（表从 64 KiB/张变成 4 GiB/张，
或用 GF(2^8) 上的 MDS 分解成 4 张 8-bit 表 + XOR 网络）。

## 三、实施步骤（每步都有可执行判据）

1. **生成端**：`gen_hybrid.cpp` 增加 `A[HY_MC_ROUNDS][16]`（每轮每字节一个 `a,b`），
   在 `fill_xor_round` 的**输入侧**用 `A_{r-1}^{-1}` 反查、**输出侧**存 `A_r(v)`；
   第 0 轮保留现有 `P0`（它已经是一个特例，`A_{-1} = P0`）。
2. **自检**：生成器内既有的回环自检（`demo_wbaes.cpp:1085-1090` 与生成端 `return 9` 分支）必须仍然通过，
   密文必须与改动前**逐字节一致**（仿射只是换坐标，不改变函数）。
3. **运行时**：`wbaes_hybrid.inc` 不改一行（这是"纯 relabeling"的判据）。
4. **反向验证**：`extract_key.py` 在改动后仍应能出钥（它按 64K 表一致性搜索，不依赖坐标）——
   如果能出钥，说明改动没有破坏自己的一致性；如果出不了，说明我建表写错了，必须先修表再谈安全。
5. **文档**：`DATA-LAYER.md` 增一节，写明"每轮不同仿射坐标，但轮边界仍可见、提取成本不变"。

## 四、为什么单独立项而不是顺手改

上一轮把 `P0i` 加到解密尾部就触发过 `return 9`（回环自检失败），原因是**内部语义与外部编码混在一起**。
轮间仿射比 P0 更危险：它同时碰 10 个轮边界、加密与解密两条路径、以及 DFA 双算的两份缓冲。
按仓库铁律，改动必须整块落地并跑通自检，不允许"先加一半、等下次"。

## 五、宽表融合的第一步：32 位 T-box 参考模型（已实测）

`demos/wbaes/fused_round_ref.cpp` 把一轮 AES 折成"四次 32 位查表 + XOR"：

```
T[p][x] = MC(·, row) · S(x)          p = 4*col + row，输出 32 位
out_col = T[p0][in[p0]] ^ T[p1][in[p1]] ^ T[p2][in[p2]] ^ T[p3][in[p3]] ^ rk_col
```

关键性质：**表路径里没有 SubBytes、没有 ShiftRows、没有 MixColumns 矩阵**——
线性层被烘进表的 32 位输出，索引置换就是 ShiftRows。

实测（2000 组随机输入/轮密钥，与明文轮逐字节比对）：
```
PASS: fused 32-bit T-box round == SubBytes+ShiftRows+MixColumns+AddRoundKey on 2000 vectors
```

这是融合的判据基线：先证明"折进表里"是对的，再谈把它接进 `gen_hybrid` 的生成流程
（接的时候还要成对处理：输出侧随机仿射 + 下一轮输入侧取逆，以及加密/解密两条路径）。

## 六、每轮不同实现（异构轮），已实测

同一轮函数可以有多种实现形状，按轮调度，代码里九轮不再同构：

| 家族 | 形状 | 轮内可见操作 |
|---|---|---|
| F0 plain | S 盒 + ShiftRows + MC 矩阵 + 轮密钥 XOR | 经典四步 |
| F1 t32 | 4 次 32 位查表 XOR，线性层烘进表 | 无 MC、无 SR 指令 |
| F2 t8 | 16 张带 MC 系数的字节表，逐字节 XOR 累加 | 无 MC 矩阵 |
| F3 keyed | 同 F1，但列密钥并入某张表的 32 位输出 | **连密钥 XOR 都没有** |

实测：2000 组随机 (state, round_key) 上四族逐字节一致
```
PASS: 4 round families agree on 2000 vectors (plain / t32 / t8 / keyed)
```
这四族现在已按轮调度进 `gen_hybrid.cpp`（下一节）。

**踩到的坑（值得记住）**：F3 最初把轮密钥并进表的**索引**（`S(x ^ k)`），三族全错。
原因是 SubBytes 非线性——常数在 S 之前 XOR 进去不会以常数的形式出来。
正确做法是并进表的**输出**：每列指定一个源，把整列密钥字 XOR 到那张表的 32 位值上，
运行时就没有密钥 XOR 这一步了。这也说明"仿射/线性技巧"在 S 盒两侧不能随意搬。

## 七、接线与导出：已完成（2026-11-17）

模型层（`fused_round_ref.cpp` / `round_families_ref.cpp`，各 2000 组随机向量 PASS）已经接进生成器：

```
gen_hybrid.cpp    SCHED_ENC / SCHED_DEC（各 9 项）+ 四个族的填充函数
                  fill_col_pair / fill_col_t32(F1,F3) / fill_col_t8(F2)
                  表尾 64 B 调度块：每 (dir,round) 一个族字节 + 校验字节
wbaes_hybrid.h    hy_mc_round 按调度字节分派四种读法；hy_scatter8 给 256 项表做位置散布
wbaes_hybrid.inc  hy_sched_valid() 在解掩后校验调度块（坏调度 → 0x8000，不给错密文）
```

每族占用的子表都在原有列槽（`HY_COL`）里面，所以槽几何、封印、掩码走查都没变；
表只长了 64 B 的调度块（69,206,016 → 69,206,080）。

**验收（三条全过）**：
- 族逐个强制 + 混合调度，密文都逐字节等于 `bb28990b4f52d7dc4c8e5cbb2839e653`：
  生成端 `table-check PASS` / `seal-check PASS`，`return 9` 回环自检通过；
- demo `vector-match: PASS` / `roundtrip: PASS`；`-DWBAES_DFA_SELFTEST` 构建仍然
  只输出垃圾（`vector-match: FAIL`），说明双旅程比对还拦得住单字节故障；
- `extract_key.py` 在换钥后的新产物上出钥（见下），所以表是一致的。

**换钥 + 导出（dl3）**：`rotate_key.py` 换成 `fd85cd856e314ea791a828d5dab81d06`，
自检密文 `e5a25174e8b329127bcaac8f3297e16e`；clean/max 两个产物 vector-match 与 roundtrip 均 PASS。

**必须同时写清的一点（异化的代价）**：F1/F2/F3 的宽表/系数表存的是
`MC[row][k]·S(x^k)`，没有 F0 那种 Q 网络随机双射，所以提取反而更容易——
`extract_key.py` 现在支持这三种形状，28 s 出钥（dl2 是 5 s，多出来的时间是掩码 keystream
要走到表尾读调度块）。详见 `DATA-LAYER.md` 第七节。异构买到的是"代码/表形状不统一"，
不是提取难度；不要把 dl3 当加固版本宣传。

F3（`HY_FAM_T32K`）是唯一必须放弃完整输出双射的族：没有重编码步，输出编码只能是仿射
`a·x^b`，否则四张表的 XOR 无法保持编码。调度里只放了 2 轮（enc 2、7 / dec 4、8）。

> 上面这一段的最后两句只对 dl3 成立。dl4 起 F3 也有完整随机边界（见第八节）。

## 八、dl4：每个异构族补齐内部编码（2026-11-17，实测）

### 缺口在哪
dl3 的问题不是"少一张 64K 表"，而是 lane 的值本身没有秘密编码：

- 第 0 轮的输入双射 `HY_P0` 在 `__TEXT,__const` 里（运行时要用，公开），所以"下标 → 明文"
  是已知的；`extract_key.py` 就是先把它读出来再取逆。
- 于是 F1/F2/F3 的行 `MC[row][k]·S(pt^k)`：MixColumns 每行都有一个系数为 1 的 k，
  取那一行直接得 `S(pt^k)`，一次反 S 盒就是密钥字节。

### 现在的结构（F0 不变，其余三族同构）
```
lane[row][k][x] = E[row][k][ MC[row][k] · S(x) ]          E = 随机 256 元素双射
acc             = (E0⁻¹[a0] ^ E1⁻¹[a1] ^ key?) ^ (E2⁻¹[a2] ^ E3⁻¹[a3])
out             = P[r][dst][ acc ^ key? ]                 P = 随机 256 元素双射（轮边界）
```
- **输入侧**：仍是上一阶段的 `P[r-1][dst]`。ShiftRows/InvShiftRows 是位置的一一映射，
  所以每张表的下标各有自己的随机双射，取逆存在上一阶段的表里。dl3 已经有这一层，本次没动。
- **输出侧（新增）**：每条 lane 一个随机双射；它的取逆只出现在 64K 组合表里
  （表内是 `E0⁻¹[a] ^ E1⁻¹[b]`），一张 256 项表无论怎样都放不下这种逆，所以
  "读一行 → 反 S 盒 → 密钥"没有落点。
- **轮边界**：256 项表做完整随机双射（F3 也一样，不再是仿射）。
- **F3 的密钥**：仍然并进第一张 64K 组合表的输出，运行时没有密钥 XOR。

### 为什么不是"线性掩码 + 在编码域里 XOR"
设计稿的原话是"encode after the linear layer，让 XOR 发生在编码域里"，那对应的是每行一个
GF(2)-线性掩码（只有线性映射才与 XOR 交换）。实测这条路不成立：第 0 轮的 `HY_P0` 是公开的、
明文已知，于是每个候选密钥字节都能用线性代数判掉——"存在 8×8 线性映射 `L` 使
`v_i = L(S(pt_i^kc))`" 是 256 个方程、8 个未知数的可解性问题，8 个输出位各解一次即可。

同一把钥、同一张表，只把 lane 掩码换成线性（其余结构不动，密文仍逐字节等于 `abe296ee…`）：

```
GF(2)-线性 lane 掩码 : 16 张表全部唯一解，0.11 s 出全钥 755e563b…（另外 13 s 仍是掩码流）
随机 lane 双射       : 16 张表无唯一解（全 0xff），这套线性代数攻击一个字节也拿不到
```

所以 lane 只能是随机双射，XOR 只能退到两条 lane 解完之后做。

### 数据结构与代价
| | dl3 | dl4 |
|---|---|---|
| F1/F2/F3 表值 | `MC[row][k]·S(x)` | `E[MC[row][k]·S(x)]` |
| 每列 64K 组合表 | 0 | 8（512 KiB） |
| 每列查表次数 F1/F3 | 8 | 16 |
| 每列查表次数 F2 | 20 | 28 |
| 表总长 | 69,206,080 | 69,206,080 |

- 8×64K = 512 KiB 落在列槽原有空洞里（槽 768 KiB，只有 F0 用得满），所以槽几何、封印、
  掩码走查、`HY_TOTAL` 都没变；生成时间 0.78 s → 0.92 s（多写 36 MiB）。
- **F3 放弃了"无重编码步"**：非线性边界必须有组合表，而宽表之间的 XOR 不可能保持非线性双射，
  二者不可兼得。这是本次明确付出的代价，不要再说 F3"连重编码都没有"。

### 验收（全部实测）
- 旧钥 `fd85…`：强制 F0 / F1 / F2 / F3 与混合调度，密文都是
  `e5a25174e8b329127bcaac8f3297e16e`；生成端 `table-check` / `seal-check` PASS（含 return-9 回环），
  demo `vector-match` / `roundtrip` PASS。
- 换钥 `755e563b1dffd249ef552c1bb778de29`（dl4）：自检密文
  `abe296eea2625f251ba57ed0b408272c`，同样四个强制调度 + 混合调度逐字节一致。
- `-DWBAES_DFA_SELFTEST`：三次运行三份不同的垃圾，`vector-match: FAIL` —— 双旅程比对仍然拦得住。
- `extract_key.py`：dl4_clean 27.2 s、dl4_max 27.4 s，**失败**；同一份脚本在 dl3_clean 上 27.7 s 出钥。
  dl4 的 27 s 全部是掩码 keystream 走 69 MB 的开销，不是攻击成本。

### 第 0 轮表还剩多少密钥信息（实测，不是推断）
用一个临时脚本（`diag_round0.py`，未入库）读 dl4_clean 第 0 轮的几张表：

```
col 0 k 0: 与 MC[row][k]·S(x^k) 逐格匹配最多 10/1024（纯碰撞）；256/256 个候选密钥字节都自洽
col 1 k 2: 13/1024；256/256
col 3 k 3: 11/1024；256/256
dl3_clean 同一测量: 1024/1024，且只剩唯一一个 kc（fd / 1d / d5 = 密钥字节）
```

"256/256 自洽"的意思是：把每行看成任意 256 元素双射的输出，任何候选密钥字节都能配出一组
双射使表完全吻合，所以第 0 轮的单表直读对密钥**零信息**。

**但这只是"便宜的路关了"**：表仍然自洽，跨轮攻击（BGE 类、或对解掩后的内存做差分/故障）
既没有实现也没有测量，所以 dl4 的提取成本是**未知**，不是"很高"。不要把它写成抗提取版本。
